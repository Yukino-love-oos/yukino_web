# 雪乃 AI —— 长期开发路线图

> 目标形态：**电脑上是一个常驻的桌面 AI 应用（开机自启）；手机通过 IM 或 App 随时找她；
> 她能听懂语音、说人话、回答问题、看图、看视频；后端用 DeepSeek API 或自建服务器模型。**

本文是**分阶段、可长期演进**的计划。原则：

1. **每个阶段结束都必须是一个能用的产品**，不做「大爆炸式」重写。
2. 先做**确定性高、依赖少**的部分，把有资质/合规风险的通道放到最后。
3. 每阶段有明确验收标准，不达标不进入下一阶段。

---

## 0. 需求翻译成可验收能力

| # | 需求 | 可验收的能力描述 | 当前状态 |
|---|---|---|---|
| R1 | 电脑上是个可打开的 AI 应用 | 双击图标/开机自启 → 出现窗口或托盘图标 → 点开就是聊天界面 | 🟡 有网页版，无托盘/自启 |
| R2 | 手机能连微信、QQ、抖音 | 在对应 App 里给她发消息，她能回 | ❌ 未开始 |
| R3 | 雪乃的性格与语气 | 人设一致、日语对白、清冷毒舌、有边界感 | ✅ 已实现（persona 卡 + few-shot） |
| R4 | 能发语音 | 回复带语音；能发语音条而不是只有文字 | ✅ 网页端已实现（浏览器内播放） |
| R5 | 能回答问题 | 通用问答 + 结合记忆的上下文回答 | ✅ 已实现 |

## 1. 现实约束（**先看这节，它决定优先级**）

### 1.1 各通道可行性

| 通道 | 官方能力 | 资质门槛 | 封号/合规风险 | 建议 |
|---|---|---|---|---|
| **Web / PWA**（已有） | 自由 | 无 | 无 | ✅ 基线，一直保留 |
| **桌面应用** | 自由 | 无 | 无 | ✅ 早做，体验提升最大 |
| **Telegram Bot** | 完全开放，免费 | 无（找 @BotFather 建 bot） | 无 | ✅ **第一个做**，用最简单通道验证架构 |
| **QQ 官方机器人** | [q.qq.com](https://q.qq.com) 开放平台，支持群聊/单聊/富媒体 | 需开发者注册 + 机器人审核；部分能力要资质 | 低（走官方） | ✅ 第二个做 |
| **企业微信（对接微信用户）** | 外部联系人可让**个人微信用户**与企微应用对话，有完整 API | 需注册企业主体（个体户/公司都可） | 低（官方） | 🟡 想合规接微信，走这条 |
| **微信公众号** | 客服消息接口 | 服务号需企业主体；个人订阅号权限很有限（无客服接口） | 低 | 🟡 只能做被动的"发消息-回一次" |
| **微信个人号**（第三方协议/hook） | ❌ 无官方 API | — | **极高**：违反《微信软件许可及服务协议》，普遍封号 | ❌ **不建议，也不在本计划内** |
| **抖音私信** | 开放平台有私信/评论能力 | 需**企业/个体工商户**资质 + 应用审核 | 中 | 🔴 放最后，取决于你是否有主体 |
| **WhatsApp** | Cloud API 开放 | 需企业验证 + 模板消息审核 | 低 | 可选 |

**结论（也是路线顺序的依据）：**

```
Web/PWA ──► 桌面应用 ──► Telegram ──► QQ 官方机器人 ──► 企业微信(≈微信) ──► 公众号 ──► 抖音(看资质)
   ✅已有      第1阶段        第3阶段        第4阶段            第8阶段          第8阶段      第10阶段
```

> 说明：以上是各平台**公开规则的大致情况**，具体以平台最新审核要求为准。
> 计划里把「拿不到资质」视为**正常分支**：如果抖音/微信通道最终不可行，产品依然通过
> 桌面端 + Web + QQ + Telegram 完整可用，不会白做。

### 1.2 多模态的成本/难度阶梯

| 能力 | 技术路径 | 单次成本量级 | 难度 |
|---|---|---|---|
| 看图 | 视觉模型（VLM）直接理解一张图 | 低（1 张图 ≈ 1k~3k token） | ⭐⭐ |
| 看短视频（<60s） | 抽 6~12 帧 + VLM 逐帧/拼接理解 + 音轨 ASR | 中（≈1 张图的 5~10 倍） | ⭐⭐⭐ |
| 看长视频 | 分段抽帧 + ASR 全文 + 分层摘要（map-reduce） | 高（10~50 倍），需要预算控制 | ⭐⭐⭐⭐ |

**所以视频能力一定是分阶段做：先图片 → 再短视频 → 再长视频。**

### 1.3 大模型：API 还是自建？

| 维度 | DeepSeek API | 服务器自建（Qwen2.5-7B/14B） |
|---|---|---|
| 质量（中文/日语） | **明显更好** | 7B 尚可，14B 接近但仍有差距 |
| 成本 | 按 token，日常闲聊每月几元~几十元 | GPU 租金按小时（云 GPU 通常远贵于 API） |
| 延迟 | 0.5~3 s | 本地 20~60 tok/s（看卡） |
| 隐私 | 对话出本机 | **全本地** |
| 运维 | 零 | 要管显存、并发、重启、升级 |
| 多模态 | 需另配视觉模型 | 可本地跑 Qwen2.5-VL |

**本计划的推荐（默认）：**

```
闲聊 / 复杂推理 → DeepSeek API（便宜、质量好、零运维）
隐私敏感 / 离线 / 断网兜底 → 服务器或本机 ollama 小模型
看图 / 看视频 → 本地 Qwen2.5-VL-7B 或云厂商视觉 API
```

代码里已经支持这个模式（`LLM_PROVIDER` 三级降级 + 自动兜底），后面只需扩展成**按任务路由**。

## 2. 目标技术架构

```
┌──────────────────────────── 通道适配层 (Adapters) ────────────────────────────┐
│  Web/PWA    桌面窗口    Telegram    QQ官方机器人   企业微信   公众号   (抖音)  │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                │  统一消息模型 InboundMessage / OutboundMessage
┌───────────────────────────────▼──────────────────────────────────────────────┐
│                         网关 Gateway                                          │
│  · 鉴权 / 白名单      · 幂等去重（IM 会重推）      · 限流                       │
│  · 入站队列（异步、可重试）  · 出站队列（按通道限速）                          │
└───────────────────────────────┬──────────────────────────────────────────────┘
┌───────────────────────────────▼──────────────────────────────────────────────┐
│                          核心 Core                                           │
│  · 会话路由（channel+user → session）   · 人格渲染（persona 卡）               │
│  · 记忆检索（结构化 + 向量 + 摘要）      · 好感度/情绪状态机                    │
│  · 编排（多步：转写→理解→生成→合成）     · 媒体归一化（silk/amr→wav，视频→帧+音轨）│
└───────────────────────────────┬──────────────────────────────────────────────┘
┌───────────────────────────────▼──────────────────────────────────────────────┐
│                        模型层 (Router)                                        │
│  LLM: ollama(本地) / DeepSeek API         VLM: Qwen2.5-VL / 云视觉 API        │
│  ASR: faster-whisper / SenseVoice         TTS: GPT-SoVITS（已有雪乃音色）      │
└───────────────────────────────┬──────────────────────────────────────────────┘
┌───────────────────────────────▼──────────────────────────────────────────────┐
│  存储：SQLite(单机) → PostgreSQL(多用户)   · 对象存储(图片/视频)  · 向量库      │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 关键设计决策（会决定后面能不能扩展）

| 决策 | 说明 | 为什么重要 |
|---|---|---|
| **统一消息模型** | `InboundMessage{channel, user_id, msg_id, text, media[], ts}` / `OutboundMessage{..., audios[], images[]}` | 加通道时只写适配器，核心不动 |
| **适配器即插件** | 每个通道一个 `Adapter` 类，实现 `poll()`/`send()` | 微信/抖音拿不到资质就整块不装 |
| **出站异步队列** | IM 通道有频控（如 QQ 私聊每分钟上限） | 同步会直接触发风控 |
| **幂等去重** | 按 `channel+msg_id` 去重 | IM 网关会重推，否则她会回两遍 |
| **媒体归一化** | 语音 silk/amr → 16k wav；视频 → 关键帧 + 音轨 | 各通道格式五花八门 |
| **模型路由** | 按任务类型 + 成本预算选模型 | 视频不能走贵模型，闲聊不必用大模型 |
| **会话即状态机** | 好感度/情绪/关系阶段落库 | 换通道后她仍然认识你 |
| **一切落库** | 消息、媒体、记忆、任务状态 | 排查问题 + 以后做多用户 |

## 3. 分阶段路线图

> 工期按「业余时间、一个人、边学边做」估算；每个阶段结束后都是**可交付、可使用**的状态。

### 阶段 M0 · 基线（✅ 已完成）

- 语音链路修通（GPT-SoVITS api_v2 + 正确权重配对 + 雪乃音色）
- 模块化 `app/`（config / pipeline / llm / state / tts / ui / server）
- 人格卡外置 + 标签协议 + 好感度持久化 + 防刷分
- 零依赖网页版（响应式 + PWA + 令牌鉴权 + 局域网）
- 本地 ollama 接入 + 云端 API 兜底 + 语言守卫
- 68 个单元测试

**验收**：网页/终端都能对话、能出声、能记住好感度。✅

---

### 阶段 M1 · 桌面应用化（1~2 周）— **建议下一步做**

**目标**：从「跑脚本开浏览器」变成「双击图标 / 开机自启的常驻应用」。

| 子任务 | 做法 | 说明 |
|---|---|---|
| M1.1 一键启动器 | `start.ps1` → 起后端 + 开窗口 | 已有雏形 |
| M1.2 托盘常驻 | `pystray` + `Pillow`：托盘图标、右键菜单（打开/静音/重启/退出） | 轻量，比 Electron 省 200MB |
| M1.3 应用窗口 | `pywebview`（复用系统 WebView2）打开 `app.server` 页面 | 看起来就是独立 App，不是浏览器 |
| M1.4 开机自启 | 注册表 `Run` 键 或 任务计划程序（登录后启动、失败重试） | 任务计划更可靠 |
| M1.5 单实例 + 崩溃自愈 | 端口占用检测 / 父进程守护（NSSM 或 watchdog） | 避免重复启动 |
| M1.6 健康检查 | `/api/health`，异常时托盘图标变红 + 通知 | 一眼看出哪个服务挂了 |
| M1.7 依赖服务托管 | 启动器顺带拉起 ollama 与 `api_v2.py` | 用户不用开三个窗口 |

**验收**：开机 → 托盘出现雪乃图标 → 点开是窗口 → 直接能聊；杀掉 ollama 后托盘变红并自动重拉。

**风险**：PyInstaller 打包后 GPT-SoVITS 路径问题 → 先不打包，用「启动脚本 + 快捷方式」；打包留到 M9。

---

### 阶段 M2 · 语音输入与语音消息（1~2 周）

| 子任务 | 做法 |
|---|---|
| M2.1 ASR | `faster-whisper`（small/medium，int8）或 SenseVoice；日语+中文 |
| M2.2 VAD | `silero-vad`，实现「一开口就停播」（打断） |
| M2.3 语音消息解码 | 微信/QQ 语音条是 **silk** 格式 → 用 `silk-v3-decoder` / `pilk` 转 wav，再送 ASR |
| M2.4 语音回复 | 已有 TTS；把 wav 转成各通道要求的格式（QQ 要 silk/amr，Telegram 要 ogg/opus） |
| M2.5 半双工通话模式 | 网页端「按住说话」；后期再考虑 WebRTC 全双工 |

**验收**：网页按住说话 → 她听懂并用语音回；发一条语音消息给她 → 她转写+回答。

**坑**：silk 编解码是这一阶段的真难点；ffmpeg 已随整合包自带。

---

### 阶段 M3 · 通道适配层 + Telegram（1 周）— **架构验证**

| 子任务 | 说明 |
|---|---|
| M3.1 抽象 Adapter | `BaseAdapter`: `start()` / `on_message()` / `send()` / `send_media()` |
| M3.2 消息模型与网关 | 入站队列、幂等去重、出站限速、错误重试 |
| M3.3 Telegram 适配器 | 最简单：长轮询 + `sendVoice`/`sendPhoto` |
| M3.4 会话映射 | `(channel, user_id)` → session；和网页端共享同一份好感度/记忆 |
| M3.5 管理命令 | `/reset`、`/mute`、`/status` |

**验收**：手机 Telegram 找她聊天，语音/文字互通，和网页端好感度同步。

**为什么先做 Telegram**：零门槛、API 稳定、富媒体齐全 —— 用它把「适配器架构」和「语音消息往返」跑通，后面接 QQ 只是换个适配器。

### 阶段 M4 · QQ 官方机器人（2~3 周）

| 子任务 | 说明 |
|---|---|
| M4.1 申请与配置 | q.qq.com 注册开发者 → 创建机器人 → 拿 AppID/Token/Secret |
| M4.2 接入方式 | WebSocket 事件订阅（推荐）或 Webhook（需公网 HTTPS） |
| M4.3 签名与鉴权 | 校验 `Ed25519` 签名，防止伪造回调 |
| M4.4 消息能力 | 频道/群/单聊（按审核到的权限）；富媒体上传（语音/图片） |
| M4.5 频控与重试 | QQ 有严格频率限制，出站必须排队限速 |
| M4.6 审核应对 | 机器人需审核，准备好功能说明、隐私政策 |

**验收**：QQ 里 @她 能对话，语音/图片能互通。

**风险**：审核不通过 / 能力受限 → 退化为「群聊 @触发」模式；架构不变。

---

### 阶段 M5 · 图片理解（1 周）

| 子任务 | 说明 |
|---|---|
| M5.1 媒体存储 | 图片落 `data/media/`，记录 hash，避免重复上传 |
| M5.2 VLM 接入 | 本地 `Qwen2.5-VL-7B`（约 16GB 显存，需 half）或云视觉 API |
| M5.3 图片→人格化描述 | 不是「图片里有…」的机器口吻，而是雪乃会怎么说 |
| M5.4 进入记忆 | 图片内容摘要进记忆，之后能引用（「上次你给我看的那只猫」） |
| M5.5 各通道适配 | Telegram `sendPhoto` / QQ 富媒体 / 网页上传 |

**验收**：发一张图 → 她用雪乃的语气评论，且之后能记住。

**成本控制**：单图限制 1 张/次，超过则排队或提示。

---

### 阶段 M6 · 记忆与人格深化（2 周）

| 子任务 | 说明 |
|---|---|
| M6.1 向量记忆 | `sqlite-vec` + 本地 embedding（bge-small / e5-small），替换现在的关键词召回 |
| M6.2 事实抽取 | 每 N 轮让模型抽取「关于用户的事实」，去重合并进 `memories` |
| M6.3 关系状态机 | 从「单一好感度」升级为「信任/亲密度/耐心」+ 关系阶段（陌生→熟识→亲近） |
| M6.4 作息与情绪 | 早上话少、深夜更坦白、考试周没耐心；情绪受事件影响并随时间衰减 |
| M6.5 人设评测集 | 30~50 条固定对话，每次改 prompt 后自动跑分，防止人设漂移 |
| M6.6 长对话压缩 | 超出上下文时做滚动摘要，避免「失忆」 |

**验收**：隔几天再聊，她主动提起之前的事；换通道（网页→Telegram）记忆连续；人设评测集分数不下降。

---

### 阶段 M7 · 视频理解（2~3 周）

| 子任务 | 说明 |
|---|---|
| M7.1 归一化 | `ffmpeg` 抽关键帧（按场景切换）+ 抽音轨 → 16k wav |
| M7.2 ASR 全文 | 音轨转写（含时间戳） |
| M7.3 分层摘要 | 短视频：帧+VLM 直接描述；长视频：分段摘要再合并 |
| M7.4 预算控制 | 按时长限制帧数/时长（如 >10 分钟只给摘要，不做逐帧） |
| M7.5 输出形态 | 用 2~3 句话点评，不是「视频内容摘要如下」 |

**验收**：发一个 3 分钟视频 → 30 秒内给出有观点、有人格的评价。

**成本**：长视频是**烧钱大户**，必须有硬上限。

---

### 阶段 M8 · 微信通道（合规路径，2~4 周，**依赖资质**）

按可行性从高到低：

1. **企业微信自建应用**（推荐）
   - 注册企业（个体工商户即可）→ 建应用 → 外部联系人可让**个人微信用户**与她对话
   - 有完整 API：文本/图片/语音/文件
   - 优点：合规、稳定；缺点：对方需加企微/关注
2. **微信公众号（服务号）**
   - 需企业主体 + 微信认证
   - 只能被动回复（48 小时内可发客服消息），适合「发一句回一句」
3. ❌ **微信个人号第三方协议**：明确不做（封号风险 + 违反协议）

**验收**：用个人微信通过企微/公众号与她对话，图文语音互通。

**分支**：资质拿不到 → 本阶段跳过，产品在其他通道照常可用。

---

### 阶段 M9 · 部署与运维（1~2 周，可与前面并行）

| 子任务 | 说明 |
|---|---|
| M9.1 容器化 | `Dockerfile` + `docker-compose`（app + ollama + 反向代理） |
| M9.2 反向代理 / HTTPS | Caddy 或 Nginx + Let's Encrypt（PWA、麦克风、Webhook 都需要 HTTPS） |
| M9.3 进程守护 | systemd / Docker restart policy / NSSM |
| M9.4 监控告警 | 健康检查 + 简单指标（QPS、延迟、显存、错误率）+ 邮件/Telegram 告警 |
| M9.5 备份 | SQLite 定期快照；媒体文件异地备份 |
| M9.6 安全 | 令牌、IP 白名单、限流、密钥集中管理（不用 .env 明文） |
| M9.7 打包分发 | PyInstaller 打桌面安装包（可选） |

**验收**：服务器重启后自动恢复；异常有告警；数据可回滚。

## 5. 关键技术难点与对策

| 难点 | 具体问题 | 对策 |
|---|---|---|
| **silk 语音格式** | 微信/QQ 语音条是 SILK v3，不是 wav | 用 `silk-v3-decoder` 或 `pilk`；无网络时先用 ffmpeg 试探 |
| **IM 幂等** | 平台会重推同一条消息 | 按 `channel+msg_id` 去重表，处理完记录 |
| **IM 频控** | QQ/微信出站严格限速 | 出站队列 + 令牌桶；失败指数退避 |
| **显存不够同时放 TTS+VLM+LLM** | 8GB 卡跑不下 | ① 分时加载（用完即卸）② 模型按需路由（看图时才载 VLM）③ 升级显卡或上云 GPU |
| **视频成本失控** | 长视频 token 爆炸 | 硬上限（时长/帧数）+ 预算检查 + 超限只给摘要 |
| **人格漂移** | 改 prompt 后性格变了 | 评测集 + 版本化 persona（每次改动留档对比） |
| **多通道状态一致** | 网页和 QQ 好感度不同步 | 会话按 `user_id` 全局唯一，channel 只是入口 |
| **隐私** | 聊天记录/图片落在服务器 | 明示、加密存储、可一键删除、非必要不留存 |
| **模型授权** | 雪乃音色来自 B 站 UP 免费分享 | 个人使用；**公开/商用前必须确认原作者条款**（见 `models/README.md`） |

## 8.3 部署形态定稿：**全云端**（不依赖家里电脑）

> 需求明确：**电脑不开机也要能在 QQ 上聊天，且不要求同一局域网、不要内网穿透方案。**
> 结论：后端必须 100% 跑在云上，家里那台 4060 完全不参与。

这条约束废掉了「家里跑 TTS + Tailscale 内网调用」的方案，也意味着 **TTS 必须在云上解决**。
而「日语 + 自己训练的雪乃音色」是这个决策里唯一的硬约束。

### 决策分叉：语音怎么办

| 路径 | 语音方案 | 需要 GPU | 音色 | 日语 | 月成本量级 |
|---|---|---|---|---|---|
| **A** | 云 TTS 声音复刻（CozyVoice / 火山 / 智谱等） | ❌ | 接近但**不完全等于** GPT-SoVITS 微调结果 | ⚠️ 云 TTS 的**日语复刻支持很有限** | ¥100~250 |
| **B** | 云 GPU 上自建 GPT-SoVITS（沿用现有权重） | ✅ | **100% 一致** | ✅ 原生 | ¥1200~2500（包月）|
| **B′** | 同上，但 GPU **按需自动启停** | ✅ | 同上 | ✅ | ¥200~400（按实际聊天时长）|

**关键结论（已按 8.4 实测修正）：**

- 「云 TTS 声音复刻」这条路在**日语**上受限：国内云厂商的声音复刻大多以中英文为主，
  日语复刻支持稀缺；海外（ElevenLabs 等）支持日语克隆，但国内访问不便且按字符计费很贵。
- 但**不一定要云 TTS**：GPT-SoVITS 本身支持 **CPU 推理**，实测（见 8.4）**完全可用**。
  也就是说「日语 + 雪乃原音色」在**纯 CPU 的 ECS 上就能跑**，不需要 GPU。

### 如果接受「中文对白」→ 可以省掉 GPU

雪乃的性格与语气可以完全用中文表达（人设卡已有），代价是失去日语台词这个特色。
一旦改成中文，云 TTS 复刻就非常好用，成本降到 1/10，且不需要任何 GPU。

> 这是本计划里**唯一需要你拍板的取舍**，其余技术都已就绪。

### 8.3.1 推荐形态 A：CPU ECS + 云 API 全家桶（最省心）

```
手机 QQ ──(QQ 服务器)──► 轻量 ECS 2C4G（常驻）
                           ├─ QQ 机器人（WebSocket 长连接，免公网回调）
                           ├─ LLM   = DeepSeek API
                           ├─ TTS   = 云 TTS 声音复刻（中文）
                           ├─ ASR   = 云短语音识别（QQ 语音条）
                           └─ VLM   = 云视觉 API（看图/看视频抽帧）
```

| 项 | 量级 | 说明 |
|---|---|---|
| 轻量应用服务器 2C4G | ¥60~150/月 | 只跑 Python 进程 + SQLite |
| DeepSeek API | 几十元/月 | 每天 100 轮 |
| 云 TTS（复刻音色） | 有免费额度，超出月几十元 | 按字符计费 |
| 云 ASR | 有免费额度 | QQ 语音条转写 |
| 云 VLM | 几十元/月 | 按 token |
| **合计** | **¥150~300/月** | 零 GPU、零运维负担 |

### 8.3.2 推荐形态 B′：CPU ECS + **弹性 GPU**（保留日语雪乃音色，成本可控）

```
手机 QQ ──► ECS（常驻，便宜）
              │  收到消息 → 检查 GPU 实例状态
              ├─ GPU 已开   → 直接调 TTS(:9880)
              ├─ GPU 已关   → 调云厂商 API 开机（1~3 分钟）
              │              先回文字，语音稍后补发
              └─ 空闲 10 分钟 → 自动关机（省钱）
```

| 项 | 量级 |
|---|---|
| 轻量 ECS | ¥60~150/月 |
| GPU 按量（T4 16G，¥1.5~3/小时） | 每天聊 2 小时 ≈ ¥120/月 |
| DeepSeek API | 几十元/月 |
| **合计** | **¥250~400/月** |

代价：闲置后的**第一条消息**要等 2~4 分钟才能听到语音（先回文字）。
适合「聊天集中在一两个时段」的用法；不适合全天零散使用。

**实现要点**（属于 M9 运维阶段，约 3~5 天工作量）：
- 云厂商 SDK：开机 / 关机 / 查状态 / 健康检查
- 幂等：并发消息只触发一次开机
- 降级：GPU 未就绪时先走文字回复，语音补发到同一条会话
- 兜底：开机失败 3 次则当日不再尝试，纯文字模式

### 8.3.3 QQ 接入的关键点（省掉一个大坑）

QQ 官方机器人支持 **WebSocket 长连接** 模式：

| 接入方式 | 需要公网 IP | 需要域名 + HTTPS | 需要 ICP 备案 |
|---|---|---|---|
| Webhook 回调 | ✅ | ✅ | ✅（国内服务器） |
| **WebSocket 长连接** | ❌ 只需能出网 | ❌ | ❌ |

**所以选 WebSocket 模式，云服务器可以不备案、不绑域名**，这是本项目接入 QQ 的最优路径。
（Telegram 用长轮询同理。）

另需注意：QQ 机器人需注册开发者并**提交机器人审核**；虚拟角色类机器人对内容合规较敏感，
雪乃「毒舌」人设需要在出站前过一层内容过滤（见 M4）。

## 8.4 实测：**CPU 推理完全可用，不需要 GPU**（推翻 8.3 的旧判断）

用 `configs/tts_infer_cpu.yaml`（`device: cpu / is_half: false`，权重与 GPU 版完全相同）
在本机（AMD Ryzen 7 7435H，8 物理核 / 16 线程）实测：

| 线程数 | 短句「そう。」 | 中句「それはどうかしら。」 | 长句「別に、あなたのためじゃないわ。」 |
|---|---|---|---|
| **16 线程** | 1.61 s | 3.39 s | 3.96 s |
| **2 线程**（≈2 核 ECS） | 1.86 s | 4.91 s | 10.03 s |

- 实时倍率约 **0.38~0.63x**（比实时慢，但完全够用）
- **从 16 线程降到 2 线程只慢 1.2~2.5 倍**，不是线性 8 倍
  —— 说明瓶颈有相当部分是串行的，**小机器反而性价比很高**
- CPU 模式内存常驻约 **3.1 GB 工作集 / 3.3 GB 私有**（模型全在内存里）

### 结论与规格建议

| 规格 | CPU 推理可行性 | TTS 内存 | 说明 |
|---|---|---|---|
| 2 核 4 GB | ⚠️ 勉强 | 需 3.3 GB | 内存吃紧（系统+app 会挤爆），单句 2~10 s |
| **4 核 8 GB** | ✅ **推荐** | 3.3 GB | 余量充足，单句约 2~6 s（估算） |
| 8 核 16 GB | ✅ 很舒服 | 3.3 GB | 单句约 1.5~4 s |

> 这台测试机的 CPU 是 8 核 Zen3+，单核性能明显强于多数 ECS 的共享 vCPU。
> **实际务必在目标 ECS 上跑一次 `python scripts/bench_tts.py --port 9881` 实测**，
> 再决定是否买 GPU —— 别凭估算下单。

### 因此最终的技术选型变成三选一（按成本从低到高）

| 方案 | 语音实现 | 需要 GPU | 音色 | 月成本 |
|---|---|---|---|---|
| **① 4核8G ECS**（推荐） | 同机 CPU 跑 GPT-SoVITS | ❌ **不需要** | 100% 一致 | ¥150~300 |
| ② 4核8G ECS + 云 TTS 复刻 | 调云厂商 API | ❌ | 接近但**日语受限** | ¥150~300 |
| ③ ECS + GPU 实例 | GPU 跑 GPT-SoVITS | ✅ | 100% 一致，快 2~4 倍 | ¥500~2500 |

**②之所以不推荐**：国内云 TTS 的日语复刻支持稀缺，且你只有日语参考音频 ——
用日语素材去克隆中文会带口音和音色漂移；而雪乃的中文配音是另一位声优，等于换人。

### 最适合 QQ 的呈现方式：**中文文字 + 日语音频**

现有代码每轮都会同时产出 `<ja>`（日语台词，走 TTS）和 `<zh>`（中文翻译）。
在 QQ 里可以这样发：

```
[中文文字消息]  那是当然的吧。就你而言，算说了句像样的话。
[语音条]        （用雪乃原音色朗读上面的日语原文）
```

这样**既看得懂，又听到原汁原味**，也完全避开了跨语言音色漂移问题。
这是当前信息下性价比与还原度最好的组合。
